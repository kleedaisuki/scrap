# Scrap v0.3.0 UX and Release Acceptance Specification

**Status:** implementation-ready product specification  
**Decision owner:** product  
**Audience:** desktop, domain/protocol, CLI, storage, installer, website, release engineering, and QA  
**Applies to:** `v0.3.0`  
**Supersedes:** conflicting search, record-value, desktop-command-placement, and product-page behavior in older design notes

## 1. Product outcome and scope

The release is complete when a user can create and operate a record without reaching for the pointer, immediately continue searching after a mutation, trust Exact and Regex result sets, keep several ordered values under one record identity, and launch Scrap from an installer-created desktop shortcut. The public website must present these outcomes as a product release, not as internal documentation.

This document specifies observable behavior. Internal storage layout, encryption framing, and view-model decomposition remain engineering decisions as long as they preserve the contracts below.

### 1.1 Evidence and interpretation

Repository observations made before implementation:

| Observation | Current surface | Product consequence |
|---|---|---|
| A record contains one `RecordValue`. | `Scrap.Domain.Record` and current client DTOs expose one `Value`. | Multi-value support is a domain migration, not merely an extra GUI field. |
| Search, mode, and search-scope state already exist independently. | `MainWindowViewModel` has `SearchText`, `SearchMode`, and a set-valued scope filter. | A record mutation must refresh results without reconstructing or losing those inputs. |
| **New record** is currently placed in the candidate-list header. | `MainWindow.axaml` candidate panel. | The command looks like list decoration even though it creates into the separately selected destination scope. |
| The detail preview uses a 15 px monospaced stack, while the editor inherits other text metrics. | `MainWindow.axaml`. | Masked, revealed, editing, and preview states can visibly jump or misalign. |
| The MSI currently owns a Start Menu shortcut, but no desktop shortcut. | `installer/Scrap.Installer.Windows/Package.wxs`. | v0.3.0 must add one installer-owned, per-user desktop shortcut while preserving Start discovery. |
| The current product page devotes substantial space to architecture and signing policy. | `website/src/lib/content.ts` and `ProductPage.astro`. | v0.3.0 needs a user-outcome release page rather than a documentation-shaped architecture page. |

External guidance is supportive rather than dispositive:

* Windows interaction guidance says `Enter` invokes a default button and `Escape` cancels or closes a window; WinUI further notes that a control which consumes `Enter` takes precedence over the dialog default. Avalonia provides the corresponding `Button.IsDefault` and `Button.IsCancel` behaviors. This supports native controls instead of a growing ad-hoc key handler. ([Microsoft Win32 keyboard guidance](https://learn.microsoft.com/en-us/windows/win32/uxguide/inter-keyboard), [Microsoft dialog guidance](https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/dialogs-and-flyouts/dialogs), [Avalonia Button documentation](https://docs.avaloniaui.net/controls/input/buttons/button))
* The WAI-ARIA Authoring Practices Guide requires `Escape` to close a modal dialog, keep focus within it, and ordinarily return focus to its invoker. APG is informative web guidance rather than a native-Avalonia conformance standard, but its focus model is directly useful here. ([W3C modal-dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/))
* Microsoft recommends placing a frequently needed core command directly on the application canvas and near the content it affects. That supports keeping **New record** visible while removing it from the results-panel heading. ([Microsoft commanding basics](https://learn.microsoft.com/en-us/windows/apps/design/basics/commanding-basics))
* WCAG explains that insertion focus must remain visible and that text must not be clipped or overlap after spacing changes. These are web criteria, not native-widget pixel prescriptions, so v0.3.0 uses an observable cross-platform visual test rather than claiming automatic WCAG conformance. ([W3C Focus Visible](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html), [W3C Text Spacing](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing))
* Microsoft generally advises offering a desktop shortcut unselected by default and retaining a Start entry for discovery. v0.3.0 deliberately overrides the generic desktop-default recommendation because the product requirement explicitly calls for a shortcut: the MSI creates exactly one per-user shortcut to the main GUI, owns it for repair/uninstall, and keeps the Start entry. ([Microsoft desktop guidance](https://learn.microsoft.com/en-us/windows/win32/uxguide/winenv-desktop), [Microsoft Start-entry guidance](https://learn.microsoft.com/en-us/windows/win32/shell/desktop-app-tiles-on-the-start-screen))

## 2. Binding product decisions

| Area | v0.3.0 decision |
|---|---|
| Record model | A record owns a non-empty, ordered collection of values. Identity remains `(scope, key)` and presentation policy remains record-wide. |
| Search | Only Fuzzy is a discovery/browse mode. Exact and Regex never pad the list with non-matches and show no candidates for a blank query. |
| Mutation refresh | Create/edit/delete preserves query, mode, case option, and scope filter and reruns that exact search revision. |
| Creation command | One primary **New record** command lives in the top workspace command area beside its destination-scope context; it is removed from the candidate-panel header. |
| Keyboard | Native default/cancel semantics are available in every modal; multiline value editing keeps plain `Enter` for a newline and uses `Ctrl+Enter` (`Cmd+Enter` on macOS) to save. |
| Value typography | Every editable, masked, revealed, and preview value uses the existing preview-value typography token. |
| Installer | Install, repair, and upgrade ensure one installer-owned, per-user desktop shortcut to the GUI. Uninstall removes it. Start Menu / application-list discovery remains. |
| Website | Publish a bilingual, outcome-led v0.3.0 release page with real UI images and direct downloads; remove documentation-like architecture and signing-policy sections from the primary page. |
| Microsoft signing | Not a v0.3.0 gate or work item. The product must not claim a verified publisher or signed artifact when that is untrue. |

## 3. Keyboard and focus contract

### 3.1 Shortcut map

| Context | Gesture | Required result |
|---|---|---|
| Scope create/rename dialog, focus in single-line name | `Enter` | Invoke enabled **Save** exactly once. Invalid input stays open and focuses/announces the validation error. |
| Record create/edit dialog, focus outside a multiline value editor | `Enter` | Invoke enabled **Save record** exactly once. |
| Record create/edit dialog, focus in a multiline value editor | `Enter` | Insert a newline; never save or close. |
| Record create/edit dialog, anywhere | `Ctrl+Enter`; `Cmd+Enter` on macOS | Invoke enabled **Save record** exactly once. The button exposes the shortcut in its tooltip/accessibility help. |
| Any non-busy modal | `Escape` | Invoke **Cancel/Close**, discard pending local changes, and return focus as specified below. |
| Delete confirmation | `Escape` | Cancel. There is no destructive default action. `Enter` deletes only when the destructive button itself has explicit focus. |
| Search box with results | `Enter` | Select the current candidate, or the first candidate if none is selected; load it and move focus to the candidate list. |
| Search box without results | `Enter` | No-op; no dialog and no error toast. |
| Search box | `Down` | Move to the current/first candidate when one exists. |
| Workspace | `Ctrl+K` or `/` when not editing text | Focus search and select its text. |
| Workspace | `Ctrl+N`; `Cmd+N` on macOS | Open **New record** for the explicit destination scope. |
| Workspace, no text editor focused | `Ctrl+C`; `Cmd+C` on macOS | Copy the active value of the selected record. Normal text-copy semantics win inside a text editor. |
| Revealed masked value, no modal | `Escape` | Re-mask all temporarily revealed values; do not clear the query or close the app. |

Use Avalonia default/cancel button semantics wherever possible; a window-level handler may cover application accelerators and the multiline `Ctrl/Cmd+Enter` exception. Do not implement two independent paths that can double-submit one key press.

### 3.2 Focus acceptance

1. Opening create/rename focuses the first editable identity field; opening record edit focuses the first value editor because the key is read-only.
2. Opening a delete confirmation focuses the safe **Cancel** action, not **Delete**.
3. `Tab` and `Shift+Tab` remain inside the active modal.
4. Cancelling returns focus to the command that opened the modal.
5. After a successful record save, focus returns to search unless the created/edited record is present in the refreshed result set; if present, select that row and focus the list.
6. While a save/delete request is in flight, show progress and prevent a second submission. `Escape` must not falsely report cancellation after the mutation has been sent.

## 4. Search truthfulness and post-mutation state

### 4.1 Mode semantics

| Mode | Blank query | Non-blank query | Permitted rows |
|---|---|---|---|
| Fuzzy | Browse records in the selected scope set, in stable order. | Ranked approximate discovery. | Only rows returned by the fuzzy matcher. Approximate, prefix, substring, and edit-distance candidates are expected. |
| Exact | Empty result set with an unobtrusive “Enter an exact key” prompt. | Ordinal equality under the selected case-sensitivity rule. | Every row's key equals the query under that rule. Same-key rows in different scopes are all valid. |
| Regex | Empty result set with an unobtrusive “Enter a pattern” prompt. | .NET regex `IsMatch` semantics under the selected case-sensitivity rule. | Every row's key matches the expression. Never fill remaining capacity with other records. |

Additional acceptance rules:

1. Switching from Fuzzy to Exact or Regex invalidates and removes old fuzzy rows immediately; stale rows must not remain visible while the replacement request is pending.
2. Changing query text, case sensitivity, or scope coverage likewise rejects older asynchronous responses by revision.
3. A malformed regex keeps the text, mode, case, and scope filter intact; it shows one inline localized error and zero stale candidates.
4. Search continues to target keys only. Multiple values never expand candidate count and never participate in search.
5. Stable ordering and the global candidate limit apply only after the mode's membership predicate. The implementation may return fewer than the limit; it must never “top up” Exact or Regex with non-matches.

### 4.2 Create/edit/delete refresh invariant

Let the visible search state before opening a modal be:

```text
S = (query, mode, case-sensitivity, selected search scopes)
```

After a successful record mutation:

1. close the modal;
2. preserve `S` byte-for-byte / option-for-option;
3. refresh the affected destination-scope count without replacing the logical destination selection;
4. rerun `S` immediately and accept only the newest response;
5. keep the search field and scope selector enabled and responsive.

If a newly created record satisfies `S`, it appears and becomes selected. If it does not satisfy `S` (including creation outside the selected search scopes), do **not** inject it into the result list. Keep the truthful list and show a localized success toast naming the destination scope. This resolves the apparent tension between “show my new item” and exact/regex correctness in favor of result truthfulness.

A scope-count refresh failure after a confirmed save does not roll back the save or disable search. Show the success outcome plus a retryable refresh warning, keep `S`, and allow the next search/scope interaction to retry normally.

## 5. New-record command placement

Required workspace hierarchy:

```text
[brand]  [Destination scope ▾]  [+ New record]  [Manage scopes]  [theme] [language]
[Search keys…] [Exact | Fuzzy | Regex] [Aa]                  [Search in ▾]
┌ Candidates ────────────┐  ┌ Record details ─────────────────────────┐
│ truthful result rows   │  │ value cards and record actions          │
└────────────────────────┘  └──────────────────────────────────────────┘
```

Acceptance criteria:

1. **New record** is a visible primary command in the top workspace command area, immediately adjacent to (or visually grouped with) the destination-scope selector.
2. Its tooltip/accessibility name includes the destination, for example “New record in production”. Search-scope coverage is never inferred as the destination.
3. Remove the always-visible duplicate from the candidate-panel header.
4. Keep the contextual **Create record** action in the no-results empty state; it invokes the same command and destination.
5. With no scopes, the record command is disabled/hidden and the existing **Create first scope** path is primary.

## 6. Multi-value record contract

### 6.1 Logical model and limits

```text
Record = (
  scope,
  key,
  values: NonEmptyOrderedList<RecordValue>,
  presentation: Masked | Plain,
  created_at,
  updated_at,
  revision
)
```

The smallest complete model deliberately adds no label, type, or presentation flag to an individual value.

* Cardinality is `1..32` values per record.
* Each value preserves the existing `0..64 KiB` UTF-8 contract; empty values and duplicate values remain valid.
* The aggregate UTF-8 bytes of all values are limited to 64 KiB. This preserves the existing scalar ceiling and keeps the worst-case escaped JSON form, including the legacy first-value projection, below the 1 MiB protocol-frame envelope.
* Order is stable and user-controlled. Record identity remains `(scope, key)`; values have no public identity beyond their 1-based position.
* The one record-wide presentation policy applies to every value.
* A record update replaces the ordered collection atomically under the existing record revision. Candidate metadata and record count remain per record, not per value.

### 6.2 Migration and compatibility

1. Every pre-v0.3 record migrates losslessly to `values = [oldValue]`, preserving scope, key, exact value bytes, presentation, timestamps, and revision semantics.
2. Migration is transactional and idempotent: interruption cannot expose a record with zero values or a partially migrated value collection.
3. Existing `scrap get <scope> <key>` behavior remains byte-for-byte identical for a one-value record.
4. For a multi-value record, the no-option CLI `get` returns value 1, preserving the meaning of existing scripts after a GUI user adds values. An explicit 1-based value-index option retrieves another value; an out-of-range index is a structured usage/domain error and emits no partial value.
5. Existing CLI `set` without a value-index option replaces Value 1 while preserving any tail values that an older client cannot see. Creating a record still creates one value. Explicit whole-list replacement uses the new structured input path; values remain stdin/interactive data rather than ordinary secret-bearing command arguments.
6. Old clients must receive a negotiated compatible single-value projection or a structured protocol-version error; they must never crash on an unexpected array. Exact wire-version design belongs to the protocol owner.

### 6.3 Desktop editor behavior

1. Create begins with one value editor. **Add value** appends a field, scrolls it into view, and focuses it.
2. Fields are visibly and programmatically labelled **Value 1**, **Value 2**, and so on. Remove is available only while at least two fields exist.
3. Move up/down commands provide keyboard-accessible reordering; their accessible names include the value number. Drag-and-drop is optional and cannot be the only reorder mechanism.
4. **Show while editing** is transient and applies to all fields. It never changes the saved record-wide presentation policy.
5. Cancel discards additions, removals, reorderings, and edits. Save commits the complete ordered list once.
6. When the 32-value or 64 KiB aggregate limit is reached, disable further addition/save as appropriate and show a localized inline explanation. Do not silently truncate.

### 6.4 Detail, reveal, and copy behavior

1. Render one value card per value in stored order, with a visible/programmatic number and an explicit **Copy** action.
2. A masked record masks every card with the same constant mask, independent of that value's length. Reveal/hide is per card and retains the existing 15-second automatic re-mask behavior; `Escape`, selection change, app minimization/lock, or opening an editor re-masks all cards.
3. A plain record displays every value without redundant Reveal controls.
4. Copy copies one value only. The active card is the most recently focused/selected card and defaults to Value 1; the workspace copy shortcut targets it. Do not add delimiter-based **Copy all** behavior in v0.3.0.
5. Clipboard-clearing behavior continues per copied masked value. Empty values are represented with localized UI text such as “Empty value”, while Copy still writes the actual empty string.

## 7. Value typography and caret rendering

Define one semantic desktop token, `ValueText`, from the currently shipped preview style:

```text
font-family: IBM Plex Mono, Cascadia Mono, Consolas, monospace
font-size: 15 effective px
font-weight: regular
line-height: one shared explicit value chosen to avoid glyph clipping
```

Apply it to every value editor, value preview/card, masked placeholder, and temporarily revealed value. Key text may continue to use the same family for identity, but `ValueText` is the binding contract for value surfaces. Toggling mask/reveal must not change font family, size, weight, line height, control height, or baseline.

Caret acceptance is visual and observable:

1. With the caret at the end of a value, the full last grapheme and the full caret are simultaneously visible; the caret is to the logical trailing side and does not paint over or clip the grapheme.
2. Keep at least one caret-width of usable trailing inset between content and the editor border/scrollbar. Wrapped lines and horizontal scrolling must bring both the terminal grapheme and caret into view.
3. Verify empty, one-character, long unbroken, multiline, CJK, combining-mark, emoji, and masked inputs at 100%, 125%, 150%, and 200% Windows scale and at the supported macOS/Linux scale settings.
4. The insertion caret and surrounding focus indication remain visible in Light and Dark themes; do not rely on the caret alone as the field's only focus indicator.

Avalonia documents `PasswordChar`/`RevealPassword`, multiline `AcceptsReturn`, and caret/selection positions on the same `TextBox`; retain one control and one typography path across masked and revealed state rather than swapping separately styled controls. ([Avalonia TextBox control](https://docs.avaloniaui.net/controls/input/text-input/textbox), [Avalonia TextBox API](https://docs.avaloniaui.net/api/avalonia/controls/textbox))

## 8. Installer behavior

1. A clean Windows MSI install creates exactly one `.lnk` in the current user's desktop. It targets the installed `scrap-gui.exe`, uses the Scrap icon and product name, and does not require elevation or write to the common/public desktop.
2. The install also retains one discoverable application entry in the user's Start Menu / All Apps and the existing uninstall registration. The desktop shortcut supplements rather than replaces Start discovery.
3. Repair and same-version repair restore the installer-owned desktop shortcut when it is missing and do not create duplicates.
4. Upgrade from supported prior versions creates/updates the same stable per-user shortcut. It must not leave versioned or duplicate links behind.
5. Uninstall removes the installer-owned desktop and Start Menu shortcuts while preserving user data. A separately named or retargeted user-created shortcut is not installer-owned and must not be removed.
6. The installer does not add a configuration checkbox in v0.3.0: shortcut creation is part of the requested default install behavior.

## 9. Version, GitHub Actions, and release gate

### 9.1 Version coherence

Every user-visible and package version source resolves to `0.3.0`; Git tags and release titles use `v0.3.0`. No screenshot, website card, package filename, installer metadata, application About/version output, or release note may still claim a prior version.

### 9.2 CI and release behavior

* Pull requests and pushes run restore/build/test for the .NET solution and install/check/test/build for the website. Domain migration, protocol compatibility, search membership, GUI state, keyboard routing, installer smoke tests, and website content tests are required gates.
* The release workflow runs for the exact `v0.3.0` tag (and may retain a manual dry-run path), verifies that the tag matches product/package versions, reruns required tests, builds platform assets, produces SHA-256 checksums, and only then publishes one GitHub Release.
* Build the release as a draft, attach all promised artifacts and checksums, verify the asset manifest, then publish; users must not see a nominally complete release missing assets. GitHub recommends draft-first publication where immutable releases are used. ([GitHub release documentation](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository))
* Ordinary CI uses read-only repository permission; only the release publication job receives `contents: write`. GitHub's workflow syntax makes unspecified permissions `none` after explicit permissions are declared. ([GitHub Actions permissions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax))
* Microsoft signing credentials and Authenticode are not v0.3.0 gates. Missing signing configuration must not fail an otherwise valid release, and automation/page copy must not imply a signature that was not produced and verified.
* GitHub Actions is also the deployment mechanism for the built Pages artifact; the deploy job depends on a successful site build and uses the documented `pages: write` / `id-token: write` permissions. ([GitHub Pages custom workflows](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages))

## 10. User-facing product release page

Implementation must update the rendered site under `website/`, not merely README or `docs/`.

### 10.1 Page hierarchy

1. **Hero:** the existing outcome-led promise, a visible `v0.3.0` release marker, primary platform download, secondary all-platforms action, and a real v0.3.0 application image.
2. **What's new:** three concise outcome cards—“keep related values together,” “Exact and Regex mean what they say,” and “keyboard-first creation and editing.”
3. **Workflow proof:** one real image/short sequence showing a multi-value record and one showing Exact/Regex results without unrelated rows. Images use current localized UI, not mock labels that the app does not ship.
4. **Core trust strip:** Local-first, encrypted values, GUI + CLI, open source. Claims stay bounded to observable implementation.
5. **Downloads:** version, operating system, architecture, format, file size, checksum affordance, and direct GitHub Release link for each shipped asset.
6. **Concise footer:** GitHub, license, privacy, and support.

### 10.2 Not on the primary page

Remove the architecture node diagram, daemon/IPC explanation, protocol semantics, CI process, command reference, documentation table of contents/sidebar, and dedicated signing-policy callout. Those may remain in repository documentation reached through GitHub. Do not add “Microsoft signed,” “verified publisher,” or equivalent copy. Signing work is out of scope; honesty is not.

### 10.3 Page acceptance

* Simplified Chinese and English contain the same sections and claims, with locale-correct `lang`, metadata, canonical/hreflang links, and controls.
* Download actions for launch point to the `v0.3.0` release/assets and never to a stale preview artifact.
* The page stays useful without JavaScript: product copy and download links are present in generated HTML.
* The site passes its existing type/content/layout tests and a production build. Keyboard focus is visible, controls have accessible names, screenshots have localized alt text, and reduced-motion preference is honored.
* Product copy says a record can contain several ordered values; it does not suggest that values are searchable or independently named/typed.

## 12. Explicit non-goals for v0.3.0

* Per-value names, types, tags, search, or presentation policy.
* Copy-all serialization or delimiter design.
* Cloud sync, sharing, or remote access.
* A redesign of scope identity or record identity.
* Microsoft code-signing procurement, reputation building, or Store submission.
* Turning the product landing page into an API/architecture/changelog documentation portal.
