# Whole-repository governance audit

- **Date:** 2026-09-24
- **Decision purpose:** complete the repository-wide review requested for behavior- and UI-preserving maintenance, rather than treating a passing product solution as proof that every repository surface was examined.
- **Baseline:** `d57a1e8` on `codex/codebase-governance`; `git ls-files` reported 329 tracked files before this audit's changes. The pre-existing, locally modified `Scrap.slnx` was not committed. Local solution tests tolerated those extra file entries; remote CI uses the clean tracked solution.

## Scope and method

Every tracked path was classified by owner. Reviewers examined the source and configuration files in their assigned areas at the contract and control-flow level, read relevant design records by filename, and made only evidence-backed changes. Binary images were inventoried by path, dimensions, source/copy relationship, and selected visual inspection; no claim is made that a binary asset was source-audited. Historical design and benchmark records were checked for status, references, and parseability, not reinterpreted as current product contracts. This is a maintenance audit, not a formal equivalence proof, security penetration test, license opinion, or complete manual UX test.

## Material observations and decisions

1. **The product/store/web surfaces had drifted.** All eight checked-in Store captures showed the earlier single-value editor, and four website copies inherited them, while the current application already presents indexed values and multi-value controls. After explicit user approval, the capture tool's current real-window output replaced the Store captures and their exact website copies. The live application UI, text and CSS were not altered. The showcase fixture contains one value per record, so the refreshed images show the current controls but do not visually prove ordering of two populated values.
2. **Release notes could misstate Windows trust after a rerun.** The Release workflow clobbers named assets on rerun, but previously kept any existing trust-status section. It now rebuilds that section from the signing state verified in the current run while preserving other notes. The Windows archive path now calls the same product-metadata check as Store packaging instead of maintaining a second copy. The current Store counter is `1.0.3.0`; the documented `1.0.2.0` WACK result remains historical evidence only.
3. **Small production and tooling defects had concrete owners.** A CLI global flag could consume the option-shaped value of `find --scope`; daemon activity paths reacquired the same reentrant lock; benchmark modes could create a fresh run root before rejecting an invalid output path; screenshot failures could leave a window or temporary preference directory open. Each received a focused change and regression or real-workflow check. The protocol lost one pure forwarding method; public comments describing v1-only behavior or stale initialization order were corrected.
4. **Security checks were not removed for cosmetic simplicity.** Wire envelope checks, strict UTF-8/JSON and AEAD/AAD checks, Unix socket permissions, profile-path policy, domain validation, storage API validation, and transaction-time concurrency checks guard different callers or failure modes. The earlier [security-validation audit](reviews/security-validation-audit.md) remains the governing threat-model analysis. No new duplicate or low-value check with a proven alternate owner was found in this pass.
5. **Dependencies were inspected without opportunistic upgrades.** Locked .NET restore and frozen pnpm install preserve the checked-in graphs. On this date, `dotnet package list --project Scrap.slnx --no-restore --include-transitive --vulnerable --format json` reported no known advisory for its 17 projects; the same check on the standalone screenshot and WiX projects reported none. `corepack pnpm audit --json` reported zero advisories across 375 lockfile dependencies. These are time-specific advisory-database observations, not a proof of non-exploitability or a reason to disable future audits. No manifest or lockfile was changed.

## Verification contract and limits

The final acceptance sequence is locked solution restore, Release build and tests; focused benchmark guard and screenshot capture; frozen website install, diagnostics, tests and build; real Windows archive/MSI inspection; script syntax checks; and GitHub Actions product jobs on Linux, Windows and macOS plus Windows/Linux developer-tool and release-site jobs. The Store package workflow requires its own CI-identity pull-request run or a separately authorized production manual run; ordinary `ci.yml` does not exercise Store installation. A successful suite tests the pushed commit, not uncommitted files or every possible input. Research on refactoring and defects likewise cautions against inferring behavioral equivalence from the label "refactor" alone ([FSE 2020 differentiated replication](https://2020.esec-fse.org/details/fse-2020-papers/125/On-the-Relationship-between-Refactoring-Actions-and-Bugs-A-Differentiated-Replicatio)).

Local Windows checks completed before the final cross-platform run: locked solution restore, warning-free Release build, **236/236 .NET tests**, frozen site install, zero Astro diagnostics, **13/13 site tests** and six generated pages; both standalone tool builds, the benchmark run-root guard, eight 1366×768 screenshot captures, real win-x64 MSI/ZIP packaging with checksum and archive-contract checks, PowerShell/YAML/Bash syntax checks, and relative Markdown-link resolution. The benchmark JSON evidence files were parsed as JSON; historical timing measurements were not rerun. Each check was chosen for the changed boundary, not as evidence that unrelated external systems were exercised.

Not exercised here: actual public-trust Authenticode signing, Partner Center submission, WACK on the current `1.0.3.0` candidate, a Linux Secret Service or macOS Keychain session on a user's desktop, and a full manual accessibility/usability pass. These require external identity, signing material, interactive OS services, or human evaluation and must not be described as passing merely because source checks or CI are green. Microsoft documents that .NET 10 audits transitive dependencies by default during restore ([NuGet auditing](https://learn.microsoft.com/en-us/nuget/concepts/auditing-packages)); GitHub Actions manual dispatch runs against the selected ref, not the local working tree ([GitHub workflow dispatch](https://docs.github.com/actions/managing-workflow-runs/manually-running-a-workflow)).
