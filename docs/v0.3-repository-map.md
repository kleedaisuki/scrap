# v0.3 repository map: multiple record values and interaction fixes

**Status:** investigation blackboard for the v0.3 implementation split
**Evidence base:** repository at `b90ed3f`; `Scrap.slnx` was intentionally not touched
**Scope:** dependency/data flow, migration hazards, search/UI event flow, tests, and safe work boundaries

## 1. Executive map

```text
CLI / GUI
   | application-specific models and adapters
   v
Scrap.Client -> Scrap.Protocol (length-prefixed JSON, protocol v1)
   |
   v
DaemonRequestDispatcher -> IDaemonOperations -> SqliteDaemonOperations
                                                |        |
                                                |        +-> Domain validation/search
                                                +-> Crypto <-> SQLite storage
                                                       AEAD AAD binds:
                                                       schema version + record ID + scope + key
```

The daemon is the only correct compatibility boundary for old scalar values. Both clients should receive one canonical `Values` list; neither client should detect or migrate legacy ciphertext.

The least destructive persistence design is **one encrypted aggregate per record**, not a child row per value. Keep `(scope, key)` as record identity, keep one record revision and one presentation policy, and encode an ordered, non-empty value list into the existing encrypted payload. Old payload format 1 is decoded as a singleton list; new payload format 2 is decoded as the list. This preserves atomic whole-record replacement and avoids an eager database rewrite.

### Recommended domain invariants

```text
Record identity       = (scope, key), unchanged
Record values         = ordered, non-empty sequence of UTF-8 strings
Duplicates            = preserved (a list, not a set)
Empty string          = allowed as an item, preserving v0.2 behavior
Mutation              = atomic whole-list replacement
Concurrency           = one record revision, unchanged
Presentation          = one record-level Masked/Plain policy, unless product explicitly asks for per-item policy
Search                = keys only; values never enter metadata/search/logs
```

Use one aggregate size limit that fits comfortably inside `ProtocolConstants.DefaultMaxFrameSize` (1 MiB). Keeping the current 64 KiB aggregate ceiling is the simplest compatibility choice; alternatively raise it only with frame-size and allocation tests. A count limit is also necessary to prevent thousands of empty UI rows from bypassing byte limits.

## 3. Persistence and migration decision

### 3.1 Current schema facts

`SqliteStore.CurrentSchemaVersion` is 1. `CreateVersionOne` creates one `records` row with `value_ciphertext`, `nonce`, `crypto_version`, `presentation`, and `revision`. `Migrate` only creates v1 from an empty store and otherwise rejects every version other than the current one; there is no existing upgrade migration.

Search/list projections deliberately omit ciphertext (`ListAllRecordMetadata`, `ListRecordMetadata`), so multiple values need not affect search queries or result DTOs.

### 3.2 Recommended no-rewrite migration

Use the existing per-record version field as the encrypted-payload format discriminator, with the meaning documented precisely:

| Stored format | Plaintext after AEAD decrypt | Domain result |
|---|---|---|
| 1 (existing) | Raw strict UTF-8 scalar | Singleton `Values` list |
| 2 (new) | Deterministic length-prefixed list encoding | Full ordered `Values` list |

New and edited records are written as format 2. Existing records migrate lazily on their next successful set. This needs no SQL schema bump and no startup rewrite, so rollback/readability and crash behavior remain simple. Prefer a bounded binary codec (count + byte length + strict UTF-8 bytes) over JSON guessing. Never detect format by “try parsing JSON”: an existing secret may itself be valid JSON and must remain byte-for-byte the same logical value.

If maintainers decide that `crypto_version` must describe only the AEAD envelope, add a separate `payload_version` column through a real v1 -> v2 migration. Do **not** casually increment `CurrentSchemaVersion`: the current `RecordIdentity.SchemaVersion` is included in AEAD additional authenticated data by `AesGcmRecordEncryptor.BuildAssociatedData`, and readers reconstruct it from `CurrentSchemaVersion` (`SqliteStore.ReadRecord`, `ReadJoinedRecord`, metadata readers). Merely changing 1 to 2 would make every old ciphertext fail authentication. A SQL v2 design therefore must persist or otherwise retain the original AAD version, or re-encrypt with the master key in a separately orchestrated daemon migration after key initialization.

### 3.3 Rename hazard

`RenameRecordAsync` and scope rename decrypt then re-encrypt because scope/key are bound into AEAD AAD. Today `SqliteDaemonOperations.Reencrypt` returns `new ProtectedValue(...)` with the default version 1. With the new payload format, that would silently relabel a list ciphertext as a legacy scalar. All re-encryption paths must explicitly preserve the source payload format, and tests must cover both record rename and scope rename of multi-value records.

### 3.4 Why not a `record_values` child table now

A child table creates per-value identity, ordering, nonce, revision, deletion, and migration questions that the requested product behavior does not require. It also makes record set and scope rename materially more complex. Use it only if independent value updates, per-value presentation, or value-level stable IDs become explicit requirements. The aggregate design turns the new case into the existing normal case: the encrypted record payload is opaque bytes either way.

## 4. Protocol, client, CLI, and GUI propagation

### Protocol/client

`RecordSetParams.Value` and `RecordDto.Value` are the only current secret-bearing wire DTO fields; `RecordSummaryDto` and search results contain metadata only. The locked design adds `values`, advances the current client to protocol v2, and makes the v0.3 daemon accept v1..v2 while echoing each request version. A v1 scalar update replaces index 0 and preserves an invisible tail; a v2 list update replaces the list atomically. A lingering v1-only daemon is shut down and replaced automatically during standard client bootstrap, before any mutation can be attempted. Summary/search remain unchanged.

Keep one `record.set` operation and one revision guard. Adding per-value mutation RPCs would multiply concurrency semantics without a demonstrated need.

### CLI compatibility questions that must be resolved explicitly

Current behavior is script-oriented: `scrap set <scope> <key>` reads one value from stdin and `scrap get` writes that raw value. Recommended compatibility posture:

1. Existing `set` input remains a singleton list.
2. Add an explicit structured stdin mode for multiple values (for example a JSON array); never pass secret values as command-line arguments.
3. Keep an explicit raw single-item retrieval path. Multi-item output must be structured or indexed; newline joining is not reversible because values may be multiline.
4. Avoid silently discarding additional values. If legacy `get` remains “first value,” document it prominently and add tests; otherwise return a stable validation error for multi-value records and require an explicit selector/structured mode.

The fourth point is a product decision, not an implementation detail. The safest automation contract is explicit `--index` and `--json` modes while preserving the old raw behavior for singleton records.

### GUI state

Replace `EditorValue` with an observable collection of value-row view models. Keep `EditorIsMasked` and temporary editor visibility independent, as they are now. For initial compatibility, one visibility toggle may apply to every editor row and one persisted presentation policy may apply to the whole record. The detail panel should render one reusable row per value with a per-row Copy action; global reveal can reveal/remask all rows if that is clearly labeled.

Use the preview value typography as the single reusable resource/style: currently preview is `IBM Plex Mono,Cascadia Mono,Consolas,monospace` at 15 px, while `RecordValueBox` inherits the proportional Window font and the masked glyph may fall back to a different font. A shared Avalonia style/resource for editor, revealed preview, and masked preview prevents drift.

## 5. Search and UI event-flow diagnosis

### 5.1 Search request flow

```text
SearchText setter / mode / case / scope filter
  -> ScheduleSearchAsync(immediate?)
     -> increment revision, cancel previous CTS
     -> clear SelectedCandidate + SelectedRecord + SearchError
     -> optional 220 ms debounce
     -> SearchSelectedScopesAsync
        -> GUI adapter -> ScrapClient -> record.search
        -> daemon loads metadata only
        -> Domain RecordSearch exact/fuzzy/regex
     -> revision check rejects stale response
     -> replace Candidates
```

Evidence: `MainWindowViewModel.SearchText` calls `ScheduleSearchAsync(false)`; mode/filter changes call it immediately. `ScheduleSearchAsync` lines 812-887 cancel prior work and use `_searchRevision`, but it does **not** clear `Candidates` when a new search starts. It clears candidates only after success or error.

The daemon/domain are not returning unrelated exact or regex matches: `RecordSearch.SearchExact` only adds `string.Equals` candidates, and `SearchRegex` only adds `regex.IsMatch` candidates. Tests in `tests/Scrap.Domain.Tests/SearchTests.cs` cover exact and regex filtering. Therefore the reported unrelated rows are most plausibly **stale GUI candidates displayed during debounce/request latency**, especially obvious for exact/regex.

Recommended behavior boundary:

- exact and regex: clear the visible candidate collection immediately when the query/mode changes;
- fuzzy: retaining previous ranked candidates during debounce is acceptable if intentionally desired, although a loading indication should distinguish stale content;
- all modes: stale responses remain rejected by revision, as today.

Add a GUI state-machine test with an intentionally blocked client response: start with unrelated candidates, switch to exact/regex, and assert the visible list clears before the new response completes.

### 5.2 New record -> search flow

```text
SaveRecordAsync
  -> IsBusy = true (workspace disabled)
  -> client.SaveRecordAsync
  -> CloseModals
  -> ScheduleSearchAsync(immediate: true)
  -> RefreshScopeCountAsync
  -> optionally reselect candidate by (scope,key)
  -> finally IsBusy = false (workspace enabled)
```

Two fragile points match the report:

1. `CloseModals` causes `MainWindow.OnViewModelPropertyChanged` to post `FocusSearch`, but it runs while `IsBusy` is still true and all three workspace regions are disabled through `IsWorkspaceEnabled`. The focus attempt can therefore fail; when `IsBusy` later becomes false, no second focus restoration occurs.
2. `RefreshScopeCountAsync` replaces `Scopes[index]` then writes `_selectedScope` directly and raises only `SelectedScope`/`ScopeStatus`. This bypasses the `SelectedScope` setter's `HasSelectedScope` notification and command-state path. The logical value remains non-null, but direct backing-field mutation makes binding/focus behavior unnecessarily fragile.

This is a GUI state/focus problem, not a scope/search protocol problem. Restore focus only after both modal closure and busy completion (one explicit post-mutation transition), and update the selected scope through a single invariant-preserving helper/setter. Test that after a successful create the search box is enabled/focusable and changing `SearchText` issues a request without changing scope.

`tests/Scrap.Gui.Tests/GuiBehaviorTests.cs::SaveReselectsCandidateByScopeAndKey` currently proves identity reselection but does not test focus, enabled state, or a second search interaction.

### 5.3 Keyboard flow and gaps

`MainWindow.axaml.cs::OnKeyDown` currently implements:

| Gesture | Current action |
|---|---|
| Escape | close any modal, else hide revealed value |
| Ctrl+K or `/` outside a text box | focus/select search |
| Ctrl+C outside text editing | copy selected record |
| Ctrl+N | open record editor |
| Down from search | select/focus first candidate |
| Enter from search | select/focus first candidate |

The reported gap remains real for modal acceptance: Enter never invokes `SaveScopeCommand`, `SaveRecordCommand`, or either delete confirmation. Enter in the multiline record value editor must remain a newline, so use a clear exception such as Ctrl+Enter for record save, while Enter can accept single-line scope forms and focused confirmation buttons. Escape is handled at the Window subscription, but there are no routed-key tests proving behavior when a child control handles the key first. Add view-level tests for focus-specific routing rather than only view-model command tests.

Do not turn every Enter into Save: `RecordValueBox` has `AcceptsReturn="True"`, and breaking multiline entry would be a user-visible regression.

### 5.4 Layout/typography evidence

- The New Record button is inside the candidate-list header (`MainWindow.axaml`, left panel), although creation targets `SelectedScope`, not the search-result collection. Moving it to the management/header area makes destination semantics visible and removes the misleading coupling.
- The value preview explicitly uses the mono font stack at 15 px; `RecordValueBox` has neither that font nor size and uses `PasswordChar="●"`. That explains visible/font metric drift between plain, masked, and preview states.
- All text boxes receive compact global padding `12,9`; the multiline/password editor has no dedicated inner-right padding/style. Cursor overlap should be reproduced with the actual Avalonia password template and fixed in one shared value-editor style rather than by adding ad hoc spaces to text.

## 7. Recommended non-overlapping work boundaries

1. **Domain + payload codec owner:** domain list type/invariants and deterministic codec tests. May touch Domain and a narrowly placed codec module; no GUI/CLI.
2. **Storage/daemon owner:** legacy decode/new encode, discriminator preservation, rename paths, daemon integration tests. Own `Scrap.Storage.Sqlite` and `SqliteDaemonOperations`.
3. **Protocol/shared-client owner:** DTO shape, protocol major, `Scrap.Client`, protocol tests. Publish the exact contract before CLI/GUI adapters integrate.
4. **CLI owner:** CLI models/adapter/commands/tests, based on the published contract. Preserve scalar stdin workflow.
5. **GUI interaction owner:** GUI models/adapter/view model/XAML/code-behind and GUI tests, including multi-row editing and the reported search/focus/keyboard/font/layout issues.
6. **Packaging/release owner:** version surfaces, GitHub Actions, MSI desktop-shortcut behavior, release site. `Package.wxs` currently creates only a Start Menu shortcut; the reported gap requires a per-user DesktopFolder shortcut with explicit install/uninstall verification and a stable component key path.
7. **Documentation/product-site owner:** update `scrap-design.md`, UX/release decisions, README command examples, and the Astro product release page after behavioral contracts settle. Existing design docs describe `Record = (scope,key,value,...)` and must not remain authoritative after v0.3.

Keep `Scrap.slnx` out of these tickets unless a genuinely new project is added; it already has unrelated local modifications.

## 8. Destructive compatibility checklist

- [ ] Existing database values decrypt as exactly one list item, including empty, multiline, Unicode, JSON-looking, and marker-looking strings.
- [ ] Bumping a database schema number cannot alter AEAD AAD for old rows.
- [ ] Record and scope rename preserve payload format and all values.
- [ ] A failed/cancelled mutation never leaves a partially replaced list.
- [ ] Search/list/log/error paths remain value-free.
- [ ] Existing singleton CLI pipelines keep their raw byte behavior.
- [ ] Multi-value CLI output is reversible and never delimiter-ambiguous.
- [ ] GUI creation completion restores enabled/focused search without scope reselection.
- [ ] Exact/regex never display stale unrelated rows while the next request is pending.
- [ ] Enter shortcuts do not destroy multiline editing; Escape and confirmation behavior are focus-tested.
- [ ] Masked/plain/editor/preview value text share one font resource and layout test surface.
- [ ] MSI retains Start Menu integration, creates the requested per-user Desktop shortcut, and removes only its own shortcuts on uninstall.
